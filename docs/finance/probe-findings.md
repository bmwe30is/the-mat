## Q1. Which Square field carries the Acuity ID, and which Acuity ID is it?

**Answer:** **`payment.note`** (and the identical `order.line_items[].note`). `reference_id` and order metadata are always empty. The note's format depends on era and the kind of sale: newer appointment charges **start with the Acuity appointment id**; package/gift/membership sales say **`Order #<Acuity order id>`**; recurring membership charges are **`Subscription <id> - … - <certificate code>`** (in 2020: **`<id> (<plan name>)`**, with no code); and **2020-era appointment charges carry no id at all** (just client name, date and class).

**Implications**

- Rule 1 (ID link) must parse the note with `parseSquareNote()` (`src/sources/square/note.ts`), not look for one fixed field. Store the parsed ref on `stg_square_payment` (`acuity_ref` + a ref kind).
- For 2020 the note gives nothing to link on. The link comes from the Acuity side instead (Q2: `transactionID` = Square order id).
- Unresolved appointment ids in 2026-09 (7 of 33) are payments taken this month for classes held in other months. The probe only pulled appointments *held* in the window, so this is expected; full extraction resolves them.
- 2020-era subscription notes (`<id> (<plan>)`) carry no certificate code, and none of their subscription ids reappear in newer notes, so they can't be linked to a specific certificate. Classify them as membership charges by note kind alone.
- `Subscription` charges (memberships) map to an Acuity **certificate**, not an appointment or an order. The PRD's `recon_link.acuity_kind` needs a third value, `certificate` / membership charge (or classify them as `MEMBERSHIP_CHARGE`). **This is a PRD change.**
- The 2020-era note text contains client names, so never log `note`.

## Q4. How do coupons appear (certificate, lower amountPaid, or both)? Can /certificates tell coupon vs package vs membership apart?

**Answer:** **Both.** Any code (coupon, package, gift or membership) is stored in the appointment's `certificate` field. The price after the code is applied is in **`price`**, and the list price is in **`priceSold`**. `/certificates` tells the kind through **`productType`** (`Subscription` → membership, `Package` → package, `Gift Certificate` → gift). Coupons are **not** in `/certificates`. Neither are many old Acuity-generated 8-hex-char codes, which were presumably deleted. Separately, 291 paid appointments **without** a code have `amountPaid > price`. They cluster at +10%, +15% and +20%, which looks like **tips collected in Acuity** (Square never has `tip_money`, Q7).

**Implications**

- `certificate_kind` = `certificateKind()` in this file: look up the code in `/certificates` and map `productType`; if it isn't there, a hex-8 code means an Acuity-generated certificate that no longer exists (kind unknown: `certificate_deleted`), and anything else means `coupon`.
- `stg_acuity_appointment`: rename or document the columns so `price_cents` means **charged price after code**, and add `list_price_cents` (from `priceSold`). Discount = list − price. **This is a PRD change** (§7.3 has only `price_cents`).
- The `TIP` amount_mismatch code (Square `tip_cents`) will never fire, because Square never has `tip_money` (Q7). Tips live on the Acuity side as `amountPaid − price`, so add `tip_cents` (or `overpaid_cents`) to `stg_acuity_appointment`. **This is a PRD change.**
- `paid = yes` with `amountPaid = 0` is normal for full redemptions. `paid` alone doesn't mean money moved.

## Q5. How do manual discounts at the Square register appear — order-level `discounts[]` or a changed line-item price?

**Answer:** **Neither appears: there are no register sales in the data.** Of 1066 Square payments (2020 plus 2026-09), 2 came from anything other than Acuity (`ECOMMERCE_API`) or Square Invoices. 0 of 1048 orders have `discounts[]`, and 1045 of 1046 line items are custom amounts with no catalog item. Discounts in this business happen **in Acuity** (coupons and codes, Q4), not at a Square register.

**Implications**

- The PRD's premise in §1 ('Manual discounts at the Square register') doesn't hold for this data. Keep `stg_square_order_discount` (cheap, future-proof), but expect it to be empty.
- `POS_RETAIL` will be rare or empty. Square-only payments are mostly **Invoices** (`square_product = INVOICES`, e.g. payment-plan memberships), which map to `INVOICE`.
- `SQUARE_DISCOUNT` won't explain mismatches. Look at Acuity tips/overpayments (Q4) instead.

## Q8. Highest `max` that /appointments and /orders accept; total number of orders.

**Answer:** `max` above 1000 works. A full year of appointments came back in one call (max 5000 → 1898). `/orders` returned **1482 orders in total**, from 2020-03-30 to 2026-09-29. The API's 2020 count matches the CSV export exactly (1898 = 1898, every month).

**Implications**

- Extract appointments in monthly chunks with `max=5000` (far above any month), and fail loudly if a chunk returns exactly `max`.
- `/orders` is small enough to pull in full every run (no date filter exists).
- 2 early order ids in Square notes are missing from `/orders`. They're probably from before the order history starts. They will classify as `ACUITY_ORDER` via the note anyway, but flag them in the exceptions report.
